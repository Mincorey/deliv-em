## 2. АРХИТЕКТУРА И СТЕК

- **Next.js 15.5 (App Router)** + **React 19**, TypeScript strict, Tailwind 4.
- **Supabase**: Postgres + Auth (SSR через `@supabase/ssr`), Storage (аватары), Realtime (чат, счётчик сообщений).
- **Платежи**: AnyPay (webhook + server actions), демо-режим.
- **Инфраструктура** (`lib/`): email (Mailgun/SendGrid/Resend/SMTP), rate-limiter, логгер, Sentry, аудит-лог, soft-delete.
- **Структура маршрутов**: группы `(app)` (защищённые: dashboard, tasks, couriers, messages, wallet, profile, ratings, favorites…) и `(auth)`. Server Actions в `actions.ts` рядом со страницами, плюс API-роуты (`/api/anypay/webhook`, `/api/couriers`, `/api/messages/*`, `/api/ratings/batch`, `/api/tasks/completed`).
- Объём: ~12 200 строк TS/TSX. Активная история git, есть `tsconfig.tsbuildinfo` — локально проект собирается.

Защита маршрутов реализована **в двух местах**: middleware `src/proxy.ts` (редирект неавторизованных) и серверно в `(app)/layout.tsx` (`getUser()` + `redirect('/auth')`). Дублирование тут — это плюс (defense in depth): даже если middleware не сработает, layout всё равно защитит.

### ⚠️ Важно: конвенция middleware vs версия Next
Файл называется `src/proxy.ts` с экспортом `proxy` — это конвенция **Next.js 16** (бывший `middleware.ts`). Но в `package.json` зафиксировано `next: "^15.5.15"` (то есть `<16`). Если при установке подтянется 15.5.x, **`proxy.ts` не будет распознан и middleware не запустится** — защита останется только на уровне layout (что, к счастью, работает). Нужно определиться: либо обновить Next до 16 (тогда `proxy.ts` корректен), либо вернуть имя `middleware.ts`/`export middleware` под 15.x. Проверить после `npm install`: какая версия реально встала.

## 4. 🔴 ДЕНЕЖНАЯ ЛОГИКА — КРИТИЧНО

Кошелёк (`profiles.wallet_balance`, `transactions`) — это реальные деньги (пополнение через AnyPay, комиссия 100 ₽ за поручение, возвраты). Здесь несколько серьёзных дефектов.

### 4.1. 🔴 `topUpWallet` начисляет баланс БЕЗ оплаты
`src/app/(app)/wallet/actions.ts` → `topUpWallet(amount)` после простой проверки авторизации **просто прибавляет сумму к балансу** через service-role клиент. Это «демо-режим», но если он останется доступен в проде, **любой авторизованный пользователь бесплатно пополнит себе кошелёк** на произвольную сумму. Перед запуском: убрать/закрыть фича-флагом, баланс должен расти только из подтверждённого webhook AnyPay.

### 4.2. 🔴 Неатомарные операции с балансом (race condition / двойная трата)
Везде используется паттерн «прочитать `wallet_balance` → посчитать в JS → записать новое значение»: `topUpWallet`, `createTask` (списание 100 ₽), `cancelTask` (возврат), webhook AnyPay. При параллельных запросах два процесса прочитают одинаковый баланс и затрут друг друга → потеря/дублирование денег. Аналогично `createTask`: проверка «баланс ≥ 100», затем списание — два одновременных создания задач могут увести баланс в минус.
**Решение:** перенести изменение баланса в одну атомарную SQL-операцию/RPC: `UPDATE profiles SET wallet_balance = wallet_balance - 100 WHERE id = $1 AND wallet_balance >= 100 RETURNING ...`, а запись задачи + списание + транзакцию выполнять в одной серверной функции (транзакция БД), а не четырьмя отдельными запросами.

### 4.3. 🔴 Webhook AnyPay без идемпотентности
`src/app/api/anypay/webhook/route.ts`: при статусе `paid` находит транзакцию и прибавляет сумму к балансу, но **не проверяет, не была ли эта транзакция уже зачислена**, и не меняет её статус на «обработана». Если AnyPay пришлёт колбэк дважды (а платёжные шлюзы это делают при ретраях), баланс пополнится **повторно**. Нужно: поле статуса у `transactions` (`pending/paid`), зачисление только при переходе `pending→paid` в атомарном `UPDATE ... WHERE status='pending'`, и тогда же — прибавление к балансу одной транзакцией БД.
Подпись (MD5 secret:amount:orderId) проверяется — это хорошо; но `amount` берётся из запроса и складывается с балансом — лучше брать сумму из своей записи `transactions`, а пришедшую только сверять.

### 4.4. 🟠 Деньги в `NUMERIC(10,2)` — это правильно, но в JS читаются как `number`
В коде `Number(profile.wallet_balance) + amount`. Для целых рублей с шагом 100 риск невелик, но при дробных суммах появятся ошибки округления. Рекомендую считать в копейках (integer) либо строго в БД.

Положительный момент: статусные переходы задач (`acceptTask`, `cancelTask`, `completeTask`, `confirmTask`) сделаны **атомарно** через условный `UPDATE ... WHERE status = '...'` — это правильная защита от гонок. Денежную часть нужно привести к тому же уровню.

## 5. 🔴 БЕЗОПАСНОСТЬ БД (RLS) — проверено на живой БД

### 5.1. 🔴 Клиент может сам изменить свой баланс
Политика `profiles_self`:
```sql
CREATE POLICY "profiles_self" ON public.profiles FOR ALL USING (auth.uid() = id);
```
`FOR ALL` включает UPDATE без ограничения колонок. Значит авторизованный пользователь с anon-ключом может из браузера выполнить:
```sql
update profiles set wallet_balance = 1000000, is_verified = true, role = 'courier' where id = auth.uid();
```
Для платформы с реальными деньгами это критично. **Решение:** отозвать у роли `authenticated` право UPDATE на чувствительные колонки (`wallet_balance`, `is_verified`, `role`, рейтинг) через `REVOKE/GRANT UPDATE (col,...)`, оставив пользователю правку только безопасных полей (имя, телефон, аватар, bio, privacy_settings). Все денежные изменения — только server-side под service-role/RPC.

### 5.2. 🔴 Опасные SECURITY DEFINER функции вызываемы ролью `anon`
Advisors живой БД: функции `soft_delete(table,id)`, `permanently_delete(table,id)`, `restore_deleted(table,id)`, `rls_auto_enable()` — `SECURITY DEFINER` и **доступны для вызова анонимом** через `/rest/v1/rpc/...`. То есть кто угодно без логина может вызвать `permanently_delete('tasks', '<id>')` и **физически удалить чужие записи**, обходя RLS. Срочно: `REVOKE EXECUTE ... FROM anon, authenticated` на эти функции (оставить только service_role), либо перевести в `SECURITY INVOKER`.

### 5.3. 🔴 8 представлений (VIEW) с SECURITY DEFINER (advisors: ERROR)
`audit_log_recent`, `transactions_with_audit`, `profiles_active`, `tasks_active`, `ratings_active`, `messages_active`, `feedback_active`, `deleted_records_stats` созданы как `SECURITY DEFINER` → запросы к ним выполняются с правами создателя, **в обход RLS вызывающего**. Например, `transactions_with_audit`/`profiles_active` могут отдать чужие финансовые/персональные данные. Пересоздать вьюхи как `security_invoker = true` (Postgres 15+) или ограничить доступ.

### 5.4. 🟠 RLS включён, но политик нет: `cities`, `task_invitations`
На обеих таблицах RLS включён без единой политики → клиент с anon/authenticated **не прочитает** их вовсе. Если `CitySelect` грузит города на клиенте — выпадающий список будет пустым (функциональный баг). Нужна публичная `SELECT`-политика на `cities` и корректные политики на `task_invitations` (либо подтвердить, что они читаются только через service-role).

### 5.5. 🟡 Прочее из advisors
`feedback_insert WITH CHECK (true)` и `audit_log insert true` — допустимо для своих сценариев, но стоит хотя бы привязать к `auth.uid()`/service-role. Публичный bucket `avatars` разрешает листинг всех файлов — сузить SELECT-политику. В Supabase Auth **выключена защита от утёкших паролей** (HaveIBeenPwned) — включить.

## 6. ПРОИЗВОДИТЕЛЬНОСТЬ БД (advisors)

- **20× `auth_rls_initplan`** — политики вызывают `auth.uid()` напрямую; на больших выборках это пересчитывается для каждой строки. Заменить на `(select auth.uid())` — заметный прирост.

Добавить индексы.
- **33× `unused_index` + 1× `duplicate_index`** — частично ложноположительно (БД пустая), но дубликат убрать и список пересмотреть после наполнения.

## 8. ГОТОВНОСТЬ К VERCEL

Хорошая новость: это «ванильное» Next.js-приложение без своего сервера — **Vercel подходит идеально** (SSR, server actions, API-роуты, ISR — всё нативно). Что нужно:

1. **Переменные окружения** в проекте Vercel: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `ANYPAY_*`, `NEXT_PUBLIC_APP_URL` (продакшн-домен), email-провайдер, `NEXT_PUBLIC_YANDEX_MAPS_KEY`, `TELEGRAM_*`, `SENTRY_DSN`.
2. **`NEXT_PUBLIC_APP_URL`** сейчас `http://localhost:3000` — выставить на боевой домен (webhook AnyPay и редиректы зависят от него).
3. **`allowedDevOrigins`** в `next.config.ts` содержит локальные IP (`10.117.x`, `192.168.x`) — это только для dev, на проде безвредно, но можно почистить.
4. **Webhook AnyPay** — указать в кабинете AnyPay боевой URL `https://<домен>/api/anypay/webhook`; убедиться, что путь в `PUBLIC_PATHS` middleware (уже добавлен).
5. **Версия Next и middleware** — закрыть вопрос из §2 до деплоя.
6. **Sentry** (`@sentry/nextjs`) — проверить инициализацию (нет `sentry.*.config.ts` в корне — возможно настроен только `lib/sentry.ts`; для Next-SDK нужны instrumentation-хуки).

## 9. ИДЕИ И УЛУЧШЕНИЯ

1. **Денежный модуль как единый сервис в БД.** Все операции с балансом — через RPC-функции с транзакциями и проверкой инвариантов (баланс ≥ 0). Это разом закрывает §4.1–4.3.
2. **Эскроу для поручений.** Сейчас списывается только комиссия 100 ₽, а само вознаграждение курьеру (`reward`) в денежном потоке не участвует. Для доверия стоит резервировать `reward` у заказчика при создании и переводить курьеру при подтверждении.
3. **Идемпотентные webhook'и + журнал платежей** с уникальным индексом по `anypay_order_id`.
4. **Тесты** — сейчас их нет. Минимум: юнит-тесты на денежную логику и интеграционные на статусные переходы задач (Vitest + Playwright).
5. **CI на GitHub Actions**: `next build` + `eslint` + `tsc --noEmit` на каждый PR.
6. **Серверная валидация zod во всех actions.** zod подключён; убедиться, что входные данные actions (суммы, адреса) валидируются на сервере, а не только в формах.
7. **Хардненинг функций**: всем `SECURITY DEFINER` задать `SET search_path = public` (advisors: 9 функций без него).
8. **Наблюдаемость**: довести Sentry до прод-готовности, включить уведомления об ошибках платежей.
